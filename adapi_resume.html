Le contexte, en une phrase

Je dois construire un serveur (une API REST) qui prend les données d'une base PostgreSQL déjà fournie et les envoie en JSON à qui les demande. Ce serveur servira plus tard (semaine 15) pour un projet en équipe.

Je ne dois pas concevoir la base de données, elle est déjà faite. Je dois juste la connecter et exposer des routes.

1

Étape 1 — Installer la base de données

Je lance ces trois commandes, dans l'ordre, dans un terminal :

psql -U postgres -c "CREATE DATABASE laremise;"
psql -U postgres -d laremise -f db/migration_up.sql
psql -U postgres -d laremise -f db/seed.sql
Comment vérifier que ça a marché Après l'import, la base doit contenir : 79 objets, 30 dépôts, 22 personnes, dont 32 objets "en rayon". Si les nombres ne correspondent pas, je corrige l'import avant de continuer.

Le fichier .env Il contient le mot de passe de ma base. Je l'ajoute à .gitignore AVANT mon tout premier commit. Si je l'envoie une seule fois sur GitHub, le mot de passe est compromis même si je le supprime après.

Étape 3 — Semaine 13 : construire le socle + les routes de lecture

Ce qu'il faut mettre en place avant les routes :

  • Un serveur Express qui démarreLe port vient d'une variable d'environnement, pas d'un chiffre écrit en dur.
  • Une connexion PostgreSQL avec le driver pgUn seul Pool, créé dans server/db.js, et rien d'autre.
  • Chaque route renvoie du JSONAvec le bon code de statut HTTP à chaque fois.

Les 5 routes de lecture à créer :

RouteCe qu'elle renvoieStatut
GET /api/categoriesToutes les catégories (id + libelle)200
GET /api/objetsListe des objets, avec le libellé de leur catégorie200
GET /api/objets?statut=&categorie_id=Même liste, filtrée (les 2 filtres sont facultatifs)200
GET /api/objets/:idUn objet + sa catégorie + son dépôt + le nom de la donatrice200 / 404
GET /api/depots/:idUn dépôt + sa donatrice + la liste des objets qu'il contient200 / 404
Piège à connaître pour la soutenance Un filtre qui ne trouve rien → je réponds 200 avec une liste vide.
Un identifiant qui n'existe pas (ex: /api/objets/9999) → je réponds 404.
Je dois savoir expliquer pourquoi c'est différent.

Comment gérer les 2 filtres optionnels sans risque :

Je n'ai pas le droit de construire la requête morceau par morceau (ça ouvre une faille de sécurité). J'utilise COALESCE à la place :

SELECT o.id, o.libelle, o.statut, o.prix, c.libelle AS categorie
FROM objet o
JOIN categorie c ON c.id = o.categorie_id
WHERE o.statut       = COALESCE($1::statut_objet, o.statut)
  AND o.categorie_id = COALESCE($2::integer,      o.categorie_id)
ORDER BY o.id DESC;

Si le paramètre vaut null, la condition devient toujours vraie → le filtre ne s'applique pas. Je dois savoir réexpliquer ça en soutenance.

Conseil de l'énoncé Je fais fonctionner GET /api/objets en entier (du navigateur jusqu'à la base) avant d'écrire une deuxième route.

Étape 4 — Semaine 14 : les routes d'écriture

Les 5 routes à créer, dans l'ordre logique du métier :

RouteCe qu'elle faitStatut
POST /api/personnesCrée une donatrice (nom, prenom, telephone?, adherente?)201 / 400
POST /api/depotsEnregistre un dépôt (personne_id, date_depot, type)201 / 400
POST /api/depots/:id/objetsAjoute un objet au dépôt (libelle, poids_kg, etat_arrivee, categorie_id)201 / 400
PATCH /api/objets/:id/statutChange le statut d'un objet (statut, prix?)200 / 400 / 404
GET /api/stats3 indicateurs : objets par statut, poids total reçu, poids détourné de la déchetterie200
Pourquoi PATCH et pas PUT, pourquoi pas de DELETE Je modifie une seule propriété (le statut) → PATCH, pas PUT (qui remplace tout).
Un objet ne disparaît jamais chez La Remise, il devient "recycle" → donc pas de route DELETE du tout.

Après un POST ou un PATCH, je renvoie la ressource à jour directement avec RETURNING, pas besoin de refaire un second SELECT :

INSERT INTO objet (libelle, poids_kg, etat_arrivee, categorie_id, depot_id)
VALUES ($1, $2, $3::etat_objet, $4, $5)
RETURNING *;
-- le statut prend sa valeur DEFAULT 'arrive' automatiquement
-- je ne dois PAS l'envoyer depuis le client

Ce que je dois valider avant d'écrire en base (obligatoire) :

  • Vérifier que les champs obligatoires sont présents
  • Vérifier les typespoids_kg doit être un nombre, pas une chaîne de caractères.
  • Vérifier les valeurs d'enum contre une liste blancheAvant de les envoyer à PostgreSQL, pas après.
  • Répondre 400 avec un message clairQuand les données sont invalides.
  • Ne jamais laisser une erreur PostgreSQL brute remonter au client
Le piège de l'enum Si le client envoie statut: "n_importe_quoi" et que je le transmets tel quel à PostgreSQL, la base rejette la valeur et mon serveur répond 500 par erreur.
Le bon réflexe : je vérifie moi-même la valeur AVANT de l'envoyer à la base, et je réponds 400 si elle est invalide.

6

Règle de sécurité obligatoire : jamais de concaténation SQL

Toute valeur qui vient du client (paramètre d'URL, filtre, corps de requête) doit passer par un paramètre SQL ($1, $2...). Jamais collée directement dans le texte de la requête.

// INTERDIT — permet une injection SQL
const q = `SELECT * FROM objets WHERE statut = '${req.query.statut}'`;

// CORRECT — la valeur passe à part
const q = 'SELECT * FROM objets WHERE statut = $1';
const { rows } = await pool.query(q, [req.query.statut]);

Liste complète de ce qui est interdit

Interdit 1Utiliser un ORM (Sequelize, Prisma, TypeORM…) — je dois écrire le SQL moi-même.
Interdit 2Concaténer des valeurs venant du client dans une requête SQL.
Interdit 3Versionner le fichier .env ou écrire un mot de passe en dur dans le code.
Interdit 4Mettre toutes les routes dans un seul fichier.
Interdit 5Transmettre une valeur d'enum à PostgreSQL sans l'avoir vérifiée avant.
